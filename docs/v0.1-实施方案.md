# 三省六部独立工作台 v0.1 实施方案

日期：2026-11-09  
用途：交给执行者的实施与验收依据。当前只完成方案编写，未实现、安装或迁移。  
版本含义：v0.1 是新架构的首个里程碑，不代表把现有 0.9.2 软件包直接降级为 0.1.0。

## 1. 执行摘要与约束优先级

要交付的是 DSH 内的独立工作台：左侧直接使用 better-workspace-group 现有项目树，中间显示所选部门的真实会话，右侧显示可调宽的部门树、模型配置以及任务与工作成果。每个项目的每个部门有独立 session；程序定向传递必要上下文，模型承担专业判断。多个项目可以同时运行，配置、会话、结果和停止操作互不串线。

用户已经确定的硬要求：

1. 独立主页面，不依附于某个普通聊天或丞相 Team；不要求 spawn_teammate 才能找到部门。
2. 复用现有项目树，不新建项目列表，不恢复顶部项目标签。分组不是项目。
3. 项目隔离从首版实现，服务侧检查归属，不能只过滤前端列表。
4. 右侧树状方块：丞相顶端居中；下一排中书、尚书、门下；尚书连接六部这一同级分组。六部两排展示，不能画成上下级。
5. 每个部门独立改模型，修改只影响当前项目当前部门；运行中的请求保持原配置。
6. 中央聊天优先保留空间，右栏可拖动、收起、恢复；白蓝浅色、跟随宿主的深色模式，紧凑字体。
7. 工作成果由 Agent 产生，用户在聊天中提供材料；成果区没有要求用户上传交付物的流程。
8. 使用 Git 管理版本。不创建 backup、时间戳副本或“最终版2”代替版本历史。

本文的字段、模块名和开发顺序是实施设计，不是已存在的 DSH API。与宿主真实接口有冲突时，先写明证据和适配方案；不得把虚构调用当成已验证能力。需求冲突按“用户最新指示 → 本文首版范围与已确认视觉要求 → 总体规划 → 历史资料”处理。

相关资料： [总体规划](../V1.0-工作台修复方案.md)、[视觉要求与预览](panel-design.md)、[待办](../TODO.md)、[交接入口](panel-handoff.md)。旧 Team/侧栏规则不具有新架构约束力。

## 2. v0.1 范围与完成定义

本方案建议：开发中先以丞相、工部两席跑通闭环，最终 v0.1 扩展到全部十席的独立会话与相同基础能力。两席闭环不能冒充十席完成。其余部门未接通时明确标注“尚未接通”，不能显示待命或可执行。

### 2.1 必须交付

| 能力 | 首版要求 |
|---|---|
| 页面入口 | “上朝”进入独立工作台，同页聊天，无需父会话 |
| 项目入口 | 真实接入现有项目树选择和稳定工作区 ID |
| 十席 | 丞相、三省、六部均可按需创建独立会话、直聊、恢复历史 |
| 配置 | 每席保存明确 provider/model/受支持 effort；实际运行可核对 |
| 基础交接 | 创建任务单、定向发送上下文与材料、回执、执行结果、回传 |
| 用户直聊 | 只发当前部门；切换部门保留各自草稿 |
| 成果 | 文件引用、主责部门、来源任务、真实检查、局部修改入口 |
| 运行控制 | 会话串行投递，跨项目可并行，取消准确指向运行 |
| 可靠性 | 幂等、失败/未知状态、刷新恢复、宿主重启后的对账 |
| 隔离 | 会话、配置、材料、记忆、权限、任务及文件边界验证 |
| 视觉 | 已确认三栏、调宽、居中、浅深色、手机抽屉、键盘可用 |
| 验收 | 单元/集成测试及真实 DSH GUI 双项目端到端证据 |

### 2.2 后续版本再做

完整自动化的“中书规划 → 门下审议 → 尚书派工 → 六部执行 → 成品审核”引擎、多层任务 DAG、自动重规划、无限层级子任务、自建技能市场、跨项目共享、自动迁移旧 Team、自动压缩换 session、成本统计仪表盘和进度百分比均不属于 v0.1。

首版可以由用户或丞相选择需要的部门，以单任务、单主责执行和结果回传构成闭环；不同部门的独立任务可并行，但同目录写冲突必须协调。不要为了自动化朝廷流程阻塞基础聊天和项目隔离。不要把十席常驻展示理解为进入页面就启动十次模型请求。

### 2.3 两条必须演示的业务路径

路径 A：用户在项目 A 找丞相提出明确工程任务 → 丞相通过受控交接操作提交工部任务单 → 程序创建/定位工部独立会话并发送必要材料 → 工部执行和检查 → 结构化报告登记结果与源文件 → 丞相收到定向结果并汇报。此时项目 B 同时运行独立任务，配置和消息保持隔离。

路径 B：用户在成果区点击“找主责部门修改” → 工部会话得到用户指定修改、成果版本及来源任务 → 修改原工作文件 → 新增修订记录和检查结果。无需重新启动整套三省流程。普通问答不强制生成任务。

## 3. 第一阶段必须核实的宿主能力

执行者先只读核实实际安装版本和源码；当前仓库中的调用痕迹只是调查线索。不得凭接口名字假设权限、返回值、完成语义或跨项目安全性。

建立 [宿主能力记录](host-capabilities.md)（实施时创建），每项填写：宿主/插件版本、源码路径与行号、调用签名、返回值、错误语义、最小验证、结论、需改动的仓库。状态只能是“已验证 / 需要扩展 / 未确认 / 不支持”。

| 项目 | 要取得的证据 | 阻塞条件 |
|---|---|---|
| 主页面扩展 | 可注册独立页面、导航、卸载行为 | 只能渲染旧聊天 sidebar |
| 项目树 | 插件真实标识、稳定 workspace ID、选择事件、初始选择、重命名/移动/删除行为 | 只能读取 DOM 文本或依赖名称猜测 |
| 内嵌聊天 | 组件生命周期、传入 session ID、原生历史/附件/输入/审批能力 | 只能跳去外部聊天页 |
| 独立 session | 创建参数、准确 ID、工作目录、角色配置、创建幂等/可查询性 | 只能扫描“最新会话”猜 ID |
| 消息投递 | 指定 session、文本、附件、消息 ID、接收回执 | 只能把文本塞进当前输入框 |
| 运行关联 | hostRunId 与消息/dispatch 的关联、终态、取消、重启查询 | 只有通用 idle 状态且无可追溯终态 |
| 模型目录 | provider/model ID、effort 枚举、可用状态、实际请求配置 | 只能改全局默认或无法核对生效 |
| 配置/工具权限 | 会话独立配置、技能绑定、宿主审批和写入边界 | 角色提示词承担实际权限控制 |
| 材料/记忆 | 附件授权引用、检索范围、全局记忆注入的开关与作用域 | 无法阻止其他项目材料自动进入 |
| 存储 | 宿主允许的位置、原子更新/事务、版本、事件恢复 | 仅浏览器 localStorage 保存任务账 |
| 主题/构建 | 宿主主题令牌、真实客户端构建和加载方式 | 改源码但当前 GUI 未加载 |

项目树可能只提供 workspaceId，没有另一个 projectId。此时在插件中生成稳定 projectId，并与 hostWorkspaceId 建唯一绑定；不要强迫宿主增加同义标识。若宿主原生 ID 足够稳定，也可使用该 ID 作为内部项目键，须记录决定。绝不能用目录名、树行号或显示名称作主键。

若缺少核心能力，交付最小宿主扩展提案和可复现证据。先完成不依赖该能力的纯逻辑、测试和视图工作；明确阻塞集成部分，不以假数据宣布完成。若需要修改本仓库外的宿主或第三方插件，说明具体仓库与变更边界，由该处适用权限控制；不要直接改安装包内的 app.asar 当成可维护实现。

DS Bot 仅为页面组织参考。当前没有核实其真实上游地址、版本或许可证。需要借用代码时先核实并记录授权；不为寻找参考引入第二套会话运行时。

## 4. 分层与复用策略

建议分为四层：工作台 UI → 项目服务/任务服务 → 会话及宿主适配层 → DSH 原生能力。任务调度必须在可持续运行的服务侧，关闭页面不会停止派发和结果处理。UI 订阅投影，不承担唯一调度者职责。

| 模块（建议名称） | 职责 |
|---|---|
| WorkspaceAdapter | 承接现有树选择、稳定 ID、生命周期 |
| SessionAdapter | 创建/查询 session、投递、运行查询/取消、原生聊天接入 |
| ModelAdapter | 目录、参数校验、明确配置快照与实际生效核对 |
| ProjectService | 项目和部门绑定、归属校验、并发版本更新 |
| ContextBuilder | 按任务构建最小上下文包、校验材料及版本 |
| DispatchService | 持久队列、幂等、单会话串行、公平并发 |
| ResultService | 校验报告、关联运行、成果登记和回传 |
| Reconciler | 启动对账、断线恢复、未知状态核查 |
| WorkbenchView | 三栏、树、会话容器、任务与成果、设置 |

这些是内部职责边界，不要求为了形式拆成十个软件包。先用本仓库技术栈，优先已有依赖；新增依赖需说明必要性。

现有[策略入口](../index.js)可参考角色职责，但必须拆除以 membership 决定身份的默认逻辑，否则所有独立会话可能都变成丞相。[旧客户端](../panel/lib/client.js)可参考主题、模型选择与注册方式，但不复用父会话/Team 投影作为状态源。[旧桥接入口](../panel/index.js)中的组建提示词不能作为新会话创建流程。[纯逻辑模块](../panel/lib/model.js)的角色定义需核对后复用。

先看 git status/diff，保护执行者开始前已有改动。不要整文件覆盖未理解的用户修改，不自动迁移旧 session。旧功能如需保留，用明确模式边界区分；新工作台不能误执行旧 Team 注入。

## 5. 身份与数据模型

以下是逻辑字段建议，不指定数据库产品。聊天正文继续由 DSH 保存；插件仅存业务账、引用和必要交接快照。所有服务入口必须从可信宿主上下文确定调用身份，再验证传入 ID；模型填写的 projectId 不能成为授权依据。

### 5.1 角色标识

| roleId | 中文 | 首版职责 |
|---|---|---|
| lead | 丞相 | 接需求、分流、协调、汇报 |
| zhongshu | 中书省 | 调查、澄清、规划 |
| shangshu | 尚书省 | 分工建议、组织交付 |
| menxia | 门下省 | 审议与整体审核 |
| libu | 吏部 | 角色和技能配置建议 |
| hubu | 户部 | 数据、表格、计算 |
| lipu | 礼部 | 文档、内容、呈现 |
| bingbu | 兵部 | 环境、调试、部署 |
| xingbu | 刑部 | 测试与风险检查 |
| gongbu | 工部 | 代码实现与工程产出 |

核对现有标识后建立显式兼容映射，尤其吏部与礼部不可混用。修改中文显示名不改变 roleId。吏部的职责不赋予它绕过用户授权修改权限或其他项目设置的权力。

### 5.2 核心记录

| 实体 | 必要字段 |
|---|---|
| Project | id、hostWorkspaceId、displayNameCache、canonicalRoot、status、schemaVersion、revision、timestamps |
| DepartmentBinding | projectId、roleId、currentSessionId(nullable)、bindingGeneration、historySessionRefs、creationRequestId、revision |
| DepartmentConfig | projectId、roleId、providerId、modelId、reasoningEffort(nullable)、rolePromptVersion、skillRefs、permissionRef、configRevision |
| Task | id、projectId、title、objective、acceptance、ownerRoleId、sourceRoleId、originMessageRef、scope、status、activeAttemptId、revision |
| Dispatch | id、projectId、taskId、attemptId、sourceSessionId、targetSessionId、bindingGeneration、contextPacketId、idempotencyKey、status、hostMessageId、timestamps |
| Attempt | id、projectId、taskId、dispatchId、sessionId、hostRunId、effectiveConfigSnapshot、state、error、startedAt、endedAt |
| ContextPacket | id、projectId、taskId、version、相关原始消息引用及必要摘录、objective、constraints、authorizationRefs、materialRefs、scope、expectedOutputs、returnTarget |
| Result | id、projectId、taskId、attemptId、reportVersion、summary、artifactRefs、checks、remainingItems、blockedReason、sourceMessageRef |
| Artifact | id、projectId、taskId、ownerRoleId、fileRef、displayName、mediaType、versionOrHash、verification、sourceResultId |
| AuthorizationRef | id、projectId、sourceHumanEvent、scope、planVersion、hostApprovalRef、status |
| Outbox/EventInbox | eventId/idempotencyKey、projectId、相关实体、处理状态、序号/游标、时间戳 |

授权记录只引用真实人类授权或宿主批准；摘要不能凭空制造批准。模型产生的“用户已同意”只是一段待核实文本。

约束：

- (projectId, roleId) 当前绑定唯一；非空 currentSessionId 不得绑定到多个项目或部门。
- task、dispatch、attempt、result、artifact 的 projectId 必须一致，跨项目引用拒绝。
- targetSessionId 在派发时固定并保存 bindingGeneration；换绑不能把旧消息自动送进新会话。
- 主键使用稳定随机 ID；名称/路径作为属性。目录解析后的规范路径用于冲突检查，不作唯一身份。
- 任务与 outbox 在同一事务内持久化；没有事务能力时实现可恢复日志并验证崩溃窗口。
- 配置用 revision/CAS 防止多个标签页互相覆盖，不能单靠浏览器锁。
- 凭据由宿主管理，只存凭据引用；不得把 token 写进上下文、任务账或日志。

### 5.3 页面本地状态

selectedRole、panelWidth、panelCollapsed 等可按“宿主用户/实例 + projectId”保存到本地。草稿还需 roleId 和 session/bindingGeneration；切换项目不能覆盖另一部门草稿。只作为 UI 恢复数据，不能取代持久任务账。宿主已有草稿管理时优先复用，不保存第二份相互竞争的草稿。

## 6. 会话创建、配置与模型切换

1. 项目首次进入时创建项目业务记录和十席配置初值，不自动发模型请求。
2. 首次明确开始聊天或收到授权派工时，按需创建该部门 session。
3. 服务获取 projectId+roleId 创建锁，读取已有绑定；已有可用会话直接使用。
4. 带 creationRequestId 调用经验证的宿主创建能力，保存准确返回 ID 和绑定。超时先查证，不能直接再建。
5. 若创建成功但绑定保存失败，保留恢复记录，按 requestId 查回并补绑定。宿主若无对应查询，显示“创建结果待核实”，要求明确恢复，不扫描最新会话猜归属。
6. 独立会话的角色身份由可信 projectId+roleId 绑定注入，不能依赖 Team membership 或让模型自报角色。
7. session 被删除或不可访问时标记 unavailable，保留旧引用。提供显式新建接续会话，必要摘要与材料经过选择后传入，旧历史不删除。

新项目初始化时把宿主默认配置解析成明确值快照；以后全局默认变化不追改已初始化项目。所有模型选项来自真实目录，不写死预览中的模型或 effort。

保存模型设置只更新该部门 desired configRevision。一次运行在真正开始前固定 effectiveConfigSnapshot；已经开始的运行不变，等待队列尚未开始的运行使用最新合法配置，并记录版本。UI 分别显示“本次运行使用”和“下次运行使用”，不混用。

切模型不清历史、不改角色、技能或权限。新模型不支持旧 effort 时，表单要求选有效值或默认值，不透传非法枚举。目录失效/额度不足时明确失败，不静默回退其他模型。若宿主只能通过换 session 改模型，必须先形成适配设计并解决历史延续，不能偷偷丢弃会话来满足表面切换。

首版技能/权限可以使用明确的角色初值与只读展示，暂不做复杂编辑器；但实际配置和边界必须可核实。不能把首版未做技能编辑解释为允许跨项目共享可变全局预设。

## 7. 上下文交接协议与真实完成条件

### 7.1 内部操作契约

以下是拟实现的业务操作，不是现成工具名：

- dispatchTask：提交目标部门、目标、完成标准、必要材料、授权依据和返回对象。调用上下文确定源项目/源部门。
- reportTaskResult：提交 taskId/attemptId、结论、文件引用、检查、未完成项或阻塞。服务验证调用者与当前执行尝试匹配。
- requestTaskInput：明确缺失信息及影响范围，进入待用户补充，不广播所有部门。
- syncDecision：用户明确同步私聊中的某个决定到指定任务/丞相，仅发送选定内容。

可以通过宿主扩展工具暴露，也可以使用经验证的结构化宿主通道。禁止靠解析任意聊天中的“已完成”三个字更新任务；禁止让浏览器定时读取最后一条消息来假装回执协议。

默认丞相可在用户已授权范围向目标部门派发任务；部门可以提交结果和请求补充。首版不允许执行部门自主递归派发，避免环路。若用户直接要求尚书派工，可通过同一权限校验契约，权限由可信角色规则决定。

### 7.2 上下文包内容

每次交接包含：任务标识与版本、目标及完成标准、相关用户原话的引用和必要摘录、已确认约束、授权来源、允许读写范围、材料版本、需要输出什么、返回给谁。不是复制整段丞相会话。

材料引用必须在目标项目下解析。共享同一项目文件可传宿主可读取的文件引用，不重复上传；宿主附件 ID 需要验证目标 session 可访问。文件找不到/权限失效时阻塞并列出缺失项。不得把另一项目的绝对路径放进消息就视为已授权共享。

上下文预算由目标模型能力和任务决定，预留输出余量；优先保留目标、硬约束、完成标准和必要证据。材料太大时提供索引及可按需读取的引用，显示裁剪情况。若模型窗口信息不可得，使用明确的保守配置，不能虚构 token 精确值。附件、检索正文和文件内容属于材料，不得覆盖系统职责或赋予授权。

### 7.3 结果与回传

报告必须包含结果摘要、成果引用、真实检查及未完成项。代码/文档任务需可编辑源文件；纯分析任务允许没有文件，但应有可追溯结果内容，不强制伪造附件。

“宿主运行正常结束”和“业务任务完成”分开判断：收到可信结构化报告，且其对应宿主运行正常结束、成果引用有效、必要条件满足，才标记 completed。报告先到时保存候选结果等待终态；运行先结束但没有有效报告时标记 needs_attention，提供补报/核实，不显示已完成。自检通过不等于独立审核通过；首版未经过门下审核时应直说未审核。

结果登记和回传通知写入可靠 outbox。向来源会话回传的文本是一条关联原任务的结果消息，仅包含必要摘要和引用。来源会话忙时排队。回传触发汇报可以是新的模型回合，但不得再次触发相同派工；结果消息需有类型和去重键。汇报失败不撤销已完成的执行任务，显示“成果已完成，汇报待处理”。

### 7.4 局部修改

成果入口带 taskId/artifactId/当前版本进入主责会话，等待用户发送具体修改指令，不在点击时自动执行。修改用关联原任务的新修订任务或新 attempt，保留旧结果引用及变更范围；历史记录不能被覆盖成仿佛第一次就产出修订版。写文件前核对当前版本，检测到用户已修改时先合并理解，不用旧快照盲目覆盖。

## 8. 状态机、队列和恢复

### 8.1 分开维护状态

| 对象 | 建议状态 | 关键规则 |
|---|---|---|
| Department | uninitialized / idle / queued / running / unavailable | 表示会话运行情况，不代表任务结论 |
| Task | draft / queued / running / waiting_input / needs_attention / completed / failed / cancelled | 未解决项不得自动完成 |
| Dispatch | prepared / sending / accepted / unknown / rejected | 发出不等于接收；超时可能 unknown |
| Attempt | queued / running / succeeded / failed / cancel_requested / cancelled / unknown | 取消请求不等于已取消 |

draft 校验通过且授权有效后可入队；accepted 等待实际运行开始；收到运行关联后进入 running。waiting_input 仅恢复原任务所需输入，不能顺便扩大范围。failed/取消任务重试创建新 attempt，不覆盖历史。unknown 必须先对账，不能自动当失败重试。

每个 session 同时只有一个活动执行，用户直聊与系统派工经统一协调。若原生聊天绕过插件队列，适配层必须接入宿主原生队列或共享忙碌检查/原子调度；两套各自独立的“串行队列”不能防竞态。运行中补充消息仅在宿主确有 steer 能力时提供，否则明确排队下一轮，不猜测语义。

跨项目队列独立，受共享并发额度约束时公平调度，展示排队原因。A 等待输入不得长期占住可释放的全局执行槽。项目切换、面板收起、浏览器关闭只影响 UI，不发送停止请求。

### 8.2 故障处理要求

| 场景 | 必须行为 |
|---|---|
| 重复点击派工 | 相同幂等键返回同一 dispatch，不能两次执行 |
| 发送超时但可能已接收 | 标记 unknown，按请求/消息 ID 查询，查不清就待核实 |
| 重复完成事件 | 以 eventId/attemptId 去重，只登记一次结果和回传 |
| 乱序事件 | 使用宿主序列或校验当前状态；终态不被迟到 running 覆盖 |
| 页面切到 B，A 返回 | 更新 A 的数据投影，不写 B 的聊天/成果 |
| 配置并发保存 | CAS 冲突后读回，提示并重应用，不静默覆盖 |
| 绑定替换后旧运行结束 | 结果归旧 attempt，不能误标新会话已完成 |
| 点停止 | 指向该 project/task/hostRunId；等待宿主取消回执 |
| 取消和成功竞争 | 以宿主真实终态和事件证据定结果，不丢成功文件 |
| 用户刷新 | 重新读取业务账并订阅/补拉事件，不重新派工 |
| 宿主重启 | 获取调度所有权，查询非终态尝试，补结果/回执，再恢复安全队列 |
| 两个浏览器窗口 | 服务端锁/租约防止重复消费；UI 不是调度主节点 |
| 模型不可用 | 保留任务及错误，配置修复后显式重试 |
| 文件已删除 | 成果标记不可用，保留来源，不显示可打开成功 |

不要承诺外部副作用 exactly-once。宿主若不支持投递幂等，只能做到本地去重与未知状态保守核对；不可判定的窗口应留给明确恢复操作。

## 9. 项目、文件、记忆与授权隔离

所有读写服务校验“调用者可访问项目 + 目标资源属于该项目 + 操作被授权”。伪造 projectId、sessionId、taskId、artifactId、hostRunId 均应拒绝。订阅流、缓存及草稿也必须带项目键，不能使用单个全局 activeSession 变量处理回调。

文件边界需要真实规范化路径，处理 Windows 大小写、相对路径、父目录与 junction/符号链接。不要假设 workspace-write 自动阻止链接逃逸。使用宿主经验证的文件访问策略；若无法保证，明确限制受支持布局并阻止不安全的自动写入。

首版默认独立项目目录。检测到两个项目相同或重叠可写目录、指向同一实际目标的链接时，提示冲突并阻止声称独立的并行写任务；优先要求使用分离目录/独立 worktree。若增加显式串行共享模式，必须明确它不提供完全文件隔离，并按解析后的资源范围加锁。相同项目不同部门也需声明写范围，重叠写任务串行；只读任务可并行。

宿主可能默认注入全局记忆或检索其他工作区。执行者必须核对并限制部门 session 的项目记忆来源；不能只在 ContextBuilder 过滤材料却保留另一条全局自动注入路径。无法隔离的可选记忆功能先关闭并记录限制。用户偏好类全局信息与其他项目业务内容区分，不能借“全局记忆”名义带入项目机密。

外部服务、端口、终端和环境变量不是 session 天然隔离资源。工具工作目录固定在目标项目，运行参数不能跟 UI 当前选择漂移。部署/发布/发消息等操作服从用户明确授权及宿主审批；跨 session 交接不得把普通文字当成宿主批准凭据。原授权覆盖的常规操作持续执行，不为每次派工重复要求用户确认。

## 10. 页面与交互施工规范

视觉依据为[已确认设计](panel-design.md)，浅色[概念图](../dsh-image-gen/image-5eef6f14.png)和深色[概念图](../dsh-image-gen/image-ef9e9758.png)仅表达布局与配色。无需再设计一套页面；生成图字体、宽度和虚构模型不是像素规范。

### 10.1 布局

- 左：复用现有项目树及其宽度管理。其缺失时提示安装/接入问题，不悄悄生成替代树。
- 中：紧凑项目/部门标题、真实原生会话和输入框。标题及输入提示明确当前接收部门。
- 右：同一区域“部门 / 任务与成果”页签。默认展示部门树，模型设置在右区展开或受控浮层，避免增加第四列。
- 树使用稳定三列对齐布局：丞相跨三列居中；中书/尚书/门下各一列；尚书下接六部组，六部按吏/户/礼、兵/刑/工两行排列。
- 连线根据布局自适应，六部连接到同一分组，不画成吏部下辖兵部。树结构是职责展示，不是 session 父子关系。

初始尺寸建议作为调试起点：右栏约 400 CSS px，允许约 340–600 px；中央聊天尽量不少于 560 px。最终取宿主现有密度及真实可用区域校准，不按屏幕物理像素直接换算。中央与右栏不足以容纳最小尺寸时切抽屉/折叠，禁止负宽度或缩小全部文字硬塞。右栏上限同时受剩余容器宽度约束。

分隔条支持拖动、键盘方向键、可见焦点及恢复默认；使用合适 separator 语义并说明当前宽度。按项目记宽度/折叠，手机使用独立布局。缩小后仅限制当前渲染值，避免覆盖用户大屏偏好。

### 10.2 方块与模型设置

卡片主体打开会话；模型按钮只打开设置，阻止事件冒泡且有独立焦点。十席都需模型入口。卡片状态来源真实业务投影，没有运行过显示“未开始”，不是“运行中”。模型长名截断可查看全名，provider 不用猜。

保存时显示“仅当前项目的此部门生效”。运行中同时显示当前模型与待生效模型。错误应有具体原因和恢复入口，不静默重置下拉框。模型目录空时禁用保存并解释。

### 10.3 任务与成果

任务列表显示主责部门、状态、更新时间；详情展示目标、交接材料、尝试、失败原因、检查和成果。不要显示无来源完成百分比。成果显示源文件、主责部门、检查状态、打开和局部修改操作。上传入口只属于聊天材料输入。

“同步决定”必须显示接收任务/部门和将同步的内容；普通私聊不会自动广播。系统回传是有来源的任务消息，与用户原话分开标识。

### 10.4 主题、手机和空状态

尽量复用宿主语义颜色令牌。浅色白/浅蓝灰/蓝强调；深色深蓝灰/灰白文字/柔和蓝强调。覆盖输入框、下拉、弹层、连线、滚动条、焦点、禁用、错误、选中。状态不仅依靠颜色。

手机通过现有项目树入口和右侧部门抽屉切换，中央对话优先；模型设置、任务详情可全宽展示。不能把桌面树整体等比缩到难以点击。选择部门后关闭抽屉并回到该部门对话。主题切换和开关抽屉不能重建 session 或清空草稿。

必须覆盖：未选项目、插件缺失、未初始化、创建中、绑定失效、模型不可用、排队、投递未知、等待输入、任务失败、没有成果。错误文字说明发生在哪个项目/部门，不要求用户猜测。

每次改变已确认布局都附新预览供核对；实施阶段优先使用真实宿主截图。沿用现有视觉要求不需要为了交方案重复生成概念图。

## 11. 分阶段执行清单与出口

| 阶段 | 工作 | 交付与进入下一阶段条件 |
|---|---|---|
| P0 基线 | 读当前代码、Git 改动、宿主接口与项目插件 | 能力记录及阻塞表；不把推测记成支持 |
| P1 数据基础 | 项目绑定、十席角色、配置、持久化、归属校验 | 双项目配置隔离、唯一约束、事务恢复测试通过 |
| P2 两席闭环 | 丞相/工部独立 session、结构化交接、运行/结果关联 | 不开 Team 完成真实任务及回传，未知投递不重复 |
| P3 十席接入 | 同一机制扩展其他八席、角色提示与权限核对 | 十席直聊/模型配置真实可用，不自动全员启动 |
| P4 工作台 | 项目树、原生聊天、右侧树、设置、任务成果、调宽主题手机 | 同页可用，布局符合确认图和文字要求 |

| P6 验收交付 | 当前 GUI 实测、构建、文档、版本与已知问题 | 提交证据、测试命令、限制及回退说明 |

UI 静态布局可与 P1–P3 并行，但真实集成依赖已验证接口。自动化任务链留到后续，不借 P3 扩展首版范围。每阶段用小 Git 提交保留可检查差异；提交只包含本任务变更。提交和发布是两件事，不自动推送、发布或重装宿主。

如多人实施：数据/调度、宿主适配、UI、验收可分工；明确文件写范围和契约负责人，接口变动先同步。不要同时修改整个旧客户端再靠最后合并猜结果。

## 13. 构建、安装与最终交付

执行者需先核实实际宿主加载的是哪个包/构建产物。当前 GUI 是 DSH 提供的页面；启动另一台开发服务器不能证明当前 GUI 已更新。若涉及客户端插件 HMR，只有同一实现 checkout 的相关 watcher 正在构建时才能承诺自动更新；其他修改按真实构建方式构建、刷新并验证。

不要修改源文件后直接报告“页面已更新”。交付说明列出宿主版本、插件版本、实际 URL、构建命令、产物路径、刷新/重启要求，以及在当前页面取得的截图。宿主扩展未安装时，明确哪些能力仍未验证。

软件包版本与新架构里程碑分开处理：先核对根包、面板包、策略常量及安装记录的现有差异，使用适合现有发布链的下一版本；未经决定不要把 0.9.2 降级到 0.1.0。文档可继续叫“新架构 v0.1”。

执行者最终提交：

1. 源码与明确 Git 提交/差异，列清保留的原有未提交改动。
2. 宿主能力记录：已验证接口、需要的宿主/插件扩展和版本。
3. 数据结构/迁移说明、内部契约、角色和权限配置说明。
4. 测试命令、结果、A01–A28 验收记录；未通过项不得写完成。
5. 真实浅色、深色、调宽、手机和双项目运行证据。
6. 用户使用说明：首次开始、切部门、改模型、派工、成果修改、未知状态恢复。
