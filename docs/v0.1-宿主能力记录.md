### 0.4 本轮**没有**做的事（重要）

- **没有**在真实宿主里做 P0 最小验证（§3 要求的「最小验证」全部待做）。

## 2. 会话与投递能力

### 2.1 会话创建（含显式 sessionId 幂等 adopt）

**签名（Host 侧）**

```ts
// node_modules/@deepseek-ai/dsh-api-session-controller/lib/types/index.d.ts:93
create(request: SessionCreateRequest): Promise<SessionCreateValue>;
```

```ts
// lib/types/types.d.ts:279-289
interface SessionCreateRequest {
  workspaceId?: WorkspaceId;
  cwd?: string;
  sessionId?: SessionId;
  agentPreset?: string;
}
interface SessionCreateValue {
  sessionId: SessionId;
  agentPreset?: string;
}
```

**实现语义**（`lib/types/commands.js`）

| 行为 | 证据 |
| --- | --- |
| `workspaceId` 与 `cwd` 同时给 → 抛 `gateway/bad-request`（"session.create accepts workspaceId or cwd, not both"） | commands.js:107-110 |
| 未给 `sessionId` 时由宿主随机生成：`request.sessionId ?? brandString(\`session-${randomUUID()}\`)` | commands.js:111 |
| 给 `workspaceId` 但查不到 → 抛 `workspace/not-found` | commands.js:113-120 |
| 解析 cwd：`workspace?.path ?? request.cwd ?? defaultCwd`，并在调用前 `mkdir(cwd, {recursive:true})` | commands.js:121-124；agent.js:475 |
| **只有显式传了 `sessionId` 才做 adopt 校验**：`ensureSession(sessionId, cwd, request.sessionId !== undefined, agentPreset)` | commands.js:124 |
| adopt 校验：cwd 不同 → `ApiSessionCwdConflict` → `session/conflict`；preset 不同 → `ApiSessionPresetConflict` → `agent-preset/conflict` | agent.js:470-474 |
| adopt 命中（同 cwd 同 preset）→ 直接返回同一个 sessionId，不新建 | agent.js:454-512 |
| session 建成后 `workspace.attachSession(sessionId)`，失败抛 `session/workspace-attach-failed`——**此时 session 已创建**，调用方必须能对账 | commands.js:129-136 |
| JSDoc 原文："Create or idempotently adopt one ordinary Session" | index.d.ts:88-93 |

**我们的用法**：`ProjectService` 用 `projectId + roleId` 生成或查出稳定 `sessionId`（形如 `session-sansheng-<projectHash>-<roleId>`），带 `cwd = workspace.path` 与 `agentPreset` 调 `create`。同一请求重放是安全的（幂等 adopt）；cwd/preset 不一致时报错，由 Reconciler 处理而不是自动重建。

**档位**：**类型层已核实**。幂等仅来自「显式 sessionId + cwd/preset 一致」，`creationRequestId` **不参与** create 的幂等（`SessionCreateRequest` 里没有这个字段，types.d.ts:279-284）。
**未验证**：真实宿主上第二次同参 create 是否真的返回同 id（需动态验证）。

**客户端等价物**（`ctx.sessions`，浏览器侧）

```ts
// lib/types/client/contract/sessions.d.ts:80-84
create(opts?: { workspaceId?: WorkspaceId; cwd?: string; sessionId?: SessionId }): Promise<SessionId>;
```

```ts
// lib/types/client/contract/sessions.d.ts:54-63
class SessionCreateError extends Error {
  rpcError: RemoteFailure;
  requestedSessionId?: SessionId;
  name = 'SessionCreateError';
}
```

`requestedSessionId` 让「创建失败但宿主可能已经建了」变成可对账状态——这正是实施方案 §6.5 要的「按 requestId 查回」的现有替代物。**档位：类型层已核实；未验证（需动态验证宿主是否真的回填该字段）**。

### 2.2 投递 prompt（requestId、mode queue/steer）

**签名（Host 侧）**

```ts
// lib/types/index.d.ts:163
prompt(request: SessionPromptRequest, signal: AbortSignal): Promise<SessionPromptValue>;
```

```ts
// lib/types/types.d.ts:319-331
interface SessionPromptRequest {
  requestId: SessionRequestId;
  sessionId: SessionId;
  mode: 'queue' | 'steer';
  content: readonly PromptContentPart[];
  clientTimeZone?: string;
}
type PromptContentPart =
  | { type: 'text'; text: string }
  | { type: 'image'; mediaType: string; data: string; name?: string }
  | { type: 'file'; receiptId: string };
interface SessionPromptValue { accepted: true }
// :78-89, :329-331
```

**requestId 幂等是真的**（`lib/types/commands.js:290-352`）：

- `if (hasPromptRequest(agent, request.requestId)) return { accepted: true }`（:301-302）——**重复投递直接吞掉，不报错**。
- `hasPromptRequest` 扫 `inbox.nextTurn` / `inbox.nextStep`，以及 `session.snapshotEvents()` 里 `user/message` 的 `source.rpcId`（:547-561）。这意味着**跨重启也幂等**（历史事件里留了 rpcId）。
- 空内容 → `gateway/bad-request`；`clientTimeZone` 非法 → `session/invalid-time-zone`。
- `mode === 'steer'` 走 `agent.steer(message)`，否则 `agent.followup(message)`（:327-330）。
- 其它异常统一折叠为 `session/agent-busy { reason }`（:347）——**错误码粒度很粗，不能靠它区分具体原因**。

**客户端签名（浏览器侧）**

```ts
// lib/types/client/contract/session.d.ts:82-84
prompt(content: PromptContentPart[], mode: 'queue' | 'steer', signal?: AbortSignal, requestId?: SessionRequestId)
  : Promise<RemoteResult<{ accepted: true }>>;
```

注意 **`requestId` 是第 4 个可选参数**——旧插件 `panel/lib/client.js:1148-1165` 的 `deliverPrompt` 只传了前两个参数，**没有 requestId**，所以旧插件路径不具备幂等性。v0.1 必须显式传。

**`RemoteResult` 的形状**（`@deepseek-ai/dsh-typert-protocol/lib/types/types.d.ts:67-73`）：

```ts
type RemoteResult<T> = { ok: true; value: T } | { ok: false; error: RemoteFailure };
```

**我们的用法**：`DispatchService` 每条派工生成一个 `requestId`（与 `dispatchId` 一一对应并落库），投递失败重试用同一个 `requestId`。`mode` 首版固定 `'queue'`；`'steer'` 只在确认宿主行为后启用。

**档位**：**类型层已核实**（Host 幂等）／**运行时已跑过**（旧插件确实用 `binding.session.prompt([...], "queue")` 成功投递，未带 requestId）。
**未验证**：客户端第 4 参数 `requestId` 是否被正确透传到 Host（需动态验证）。

**客户端补充**：`beginSubmission(input): SubmissionHandle`（session.d.ts:73）返回 `{ requestId, abandon() }`，是官方的「先登记 echo 再发」路径；`SubmissionHandle.requestId` 的类型注释明确「pass it to prompt」。

### 2.3 取消

```ts
// lib/types/index.d.ts:181  （注意：同步返回，不是 Promise）
cancel(request: SessionCancelRequest): SessionCancelValue;
// lib/types/types.d.ts:353-359
interface SessionCancelRequest { sessionId: SessionId }
interface SessionCancelValue { accepted: true }
```

实现（`lib/types/commands.js:468-478`）：

- **只对已 attach 的 live agent 生效**，否则抛 `session/not-found`（"session ... not found (not attached)"）。
- 调用 `agent.cancel({ kind: 'user' }, { keepInbox: true })`——**保留 inbox**，排队消息不会被清掉。
- JSDoc（index.d.ts:177-181）："Cancel one active Agent turn **without dropping its pending inbox** ... acknowledgement that cancellation was **requested**"。

客户端等价物：`ISession.cancel(): Promise<RemoteResult<{accepted:true}>>`（session.d.ts:108-110）。JSDoc 补一句关键语义：**"Pending queued work remains and resumes in FIFO order after the Host reaches cancellation quiescence"**——即取消后排队任务会**继续跑**。

**我们的用法**：`Attempt` 状态机保留 `cancel_requested` 与 `cancelled` 两个态（正好对应实施方案 §8）；`cancel()` 返回只推进到 `cancel_requested`，终态必须靠 `follow` 事件或 `running` 投影落到 false 才能确认。

**档位**：**类型层已核实**。**未验证**：真实宿主上从 `cancel()` 到 `running=false` 的时延与事件序列（需动态验证）。

### 3.1 模型目录

```ts
// lib/types/index.d.ts:109
modelCatalog(): Promise<ModelCatalog>;

interface ModelCatalog {
  default: ModelSelection;
  routableProviders: readonly string[];
  groups: readonly ModelProviderGroup[];
  failures: readonly ModelCatalogFailure[];
}
```

**要点**：

**档位**：**类型层已核实**（Host 签名与形状）。**未验证**：真实宿主返回的 efforts 枚举内容（需动态验证）。

### 3.2 模型选择

```ts
// lib/types/index.d.ts:99
selectModel(request: SessionSelectModelRequest): Promise<SessionSelectModelValue>;
// lib/types/types.d.ts:91-95, :291-297
interface ModelSelection { provider: string; model: string; reasoningEffort?: string }
interface SessionSelectModelRequest extends ModelSelection { sessionId: SessionId }
interface SessionSelectModelValue { selected: ModelSelection }
```

实现（`lib/types/commands.js:145-175`）：

1. 先 `resolveAgent`（**会 resume 会话**）；
2. 模型不在目录里 → 抛 `session/model-unavailable { provider, model }`；

4. `agents.selectForNextRequest(selected)`；
5. **后台** `agentDefaultModel.saveSelection(selected)` —— **会把这个选择写成全局默认**，失败只 warn。

JSDoc（index.d.ts:94-99）："Select one Session-local model after explicitly resuming the Session; **save the default in the background**"。

> **这是 v0.1 最容易踩的坑**：`selectModel` 不是「只改这个会话」，它顺带改全局默认。所以「本项目本部门固定模型」必须由插件在**每次派发前**显式 `selectModel` 覆写，并自己持久化 desired 配置；不能指望宿主记住。

相关投影：

```ts

```

投影键名固定三个（`lib/types/types.d.ts:11-27`）：`sessionListMetadata`、`imageLimits`、`modelSelection`。这正是实施方案 §6「UI 分别显示『本次运行使用』和『下次运行使用』」的现成数据源（`lastUsed` / `next`）。

**档位**：**类型层已核实**。
**运行时已跑过（间接）**：旧插件 `panel/lib/client.js:1534-1560` 走 `remote.session.selectModel({sessionId, provider, model, reasoningEffort?})` 返回 `{ok, error:{code,message}}`，说明该 RPC 在真实宿主里存在且可调。

### 4.3 follow 事件流

```ts
// lib/types/index.d.ts:196
follow(request: SessionFollowRequest, signal: AbortSignal): AsyncIterable<SessionFollowFrame>;
// lib/types/types.d.ts:459-463, :516-527
interface SessionFollowRequest extends Pick<SessionPageRequest, 'maxMessages' | 'turnWindow'> {
  address: SessionAddress; assistantStream?: true;
}
type SessionFollowFrame =
  | { type: 'snapshot'; header: SessionWireHeader; cursor: number; records; hasMore: boolean;
      projections: SessionProjectionBaseline; assistantStream?: ... }
  | { type: 'event'; event: SessionWireEvent }
  | { type: 'assistant-stream'; frame: ... };
```

Host JSDoc（index.d.ts:190-196）："complete opening snapshot followed by **gap-free durable event frames** and optional cursorless assistant-stream frames"。

- 首帧必然是 `snapshot`（带 `cursor` 与 `projections` 基线），后续是 `event`；**assistant-stream 帧是无游标的**（不可作为状态依据）。
- `SessionAddress` 支持子会话：`{kind:'subagent'; parentSessionId; childSessionId; mode:'one-shot'|'continuable'|'unknown'}`（:386-394）。v0.1 十席走**普通会话**（`{kind:'session'}`），不用 subagent 地址，这是与旧方案的关键区别。

### 6.4 slot register / registerFactory / renderFactorySlot 语义

```ts
// node_modules/@deepseek-ai/dsh-client-ui-slots/lib/types/index.d.ts
type SlotKind = 'single' | 'list' | 'keyed' | 'chain';      // :83
type SlotScope = 'root' | 'session-maybe' | 'session';      // :85
type SlotComponent<P> = (props: P) => ReactNode;            // :343
```

**`register`**（两个重载，`SlotCore.register` @ :789-804；`SlotRegistry.register` 复用同一签名 @ registry.d.ts:85）：

| 语义 | 证据 |
| --- | --- |
| 返回**幂等 disposer**；disposer 会**递归折叠**它声明的子槽 | :777-788 |
| 注册未声明的 slot → 抛错 | :789-804 及 load-time 校验段 |
| 同一 declarer 重复声明同一 child key → 抛错 | 同上 |
| 同一 store handle 跨不同 scope 挂载 → 抛错 | 同上 |
| keyed 缺 `key` / list 缺 `id` / chain 缺 `select` → 各自抛错 | 同上 |
| **shadowing**：同 cell（single=整槽、keyed=同 key、list=同 id）按 `priority` **升序**共存，最低者渲染；ties 保留注册顺序 | :769-776 |
| **在已占用 cell 的同 priority 再注册 → 抛错并点名 occupant** | :769-776；`KindOptions` 注释复述 "same key/id/cell + same priority throws" @ :560-584 |
| 声明了 `children` 就必须消费 `renderSlot`（或仅 chain 时 `renderSlotChain`），否则**编译期**报 `'children declared but the component consumes no renderSlot'` | `RendersCheck` :591-596 |

**`registerFactory`**：

```ts
// ui-slots index.d.ts:532-534
interface RegisterFactory {
  <F>(options: RegisterFactoryOptions<F>, component: SlotComponent<FactoryComponentPropsOf<F>>): () => void;
}
// RegisterFactoryOptions @ :522-526
{ name: F; scope: FactoryDefOf<F>['scope'] } & children? & store? & inject? & locale? & slots?
```

有**类型级**碰撞检查：`FactoryCollisionCheck`（inject/input/local props 重叠 → 编译失败，:508-513）、`FactoryChildrenCheck`（子槽定义必须与 SlotMap 相符，:514-521）。

**`renderFactorySlot`**：

```ts
// ui-slots index.d.ts:395-404
type RenderFactorySlot = <F>(name: F, props: FactoryInputPropsOf<F>, options?: {
  slots?: Partial<{ [N in local]: FactoryLocalComponent<F, N> }>;
  fallback?: ReactNode;
}) => ReactNode;
interface PropsRenderFactories { renderFactorySlot: RenderFactorySlot }
```

"**每个 renderer 创建的组件都拿到 `renderFactorySlot`**"（原注释：Factory rendering capability supplied to **every** renderer-created Component）→ 插件组件里直接 `props.renderFactorySlot(...)` 即可，无需自己 import 任何东西。

相关但**禁止**的：`SlotRegistry.renderSlot(key, owner)` **运行时强制 `key === 'root'`**（registry.d.ts:150-158）。除 root 之外，任何槽都只能通过组件 props 的 `renderSlot` 渲染。

**`root` 槽禁止注册**——原注释（registry.d.ts:16-38）值得整段引用：

> "**DO NOT register here.** This is a single slot, so a second entry does not sit beside the frame — it shadows it, and a dynamically registered entry is assigned a lower priority than the shipped one, which makes it the winner: **the page would render your component alone, with every seat the frame declares gone.** For a surface of your own that floats over the whole app, register into `shell.overlay` instead (a list slot: additive, and click-through until your entry opts into pointer events)."

root 被 ui-layout 的 `AppFrame` 占据，AppFrame 在其内部声明 `sidebar` / `conversation` / `details` / `shell.overlay` 四个座位。

**`ctx.slots.inject(key, cb)`**（registry.d.ts:96-111）是**不依赖 apply 顺序**的正确姿势：槽已声明则同步跑 cb，否则等声明方 register 提交后跑；折叠时 dispose，再声明会重跑。旧插件全部用它（client.js:2006-2072），**这是对的，v0.1 继续用**。

**档位**：语义 = **类型层已核实**（文档注释极详细，逐条有行号）。
**运行时已跑过**：`register` + `inject` 组合（旧插件 5 处注册在真实宿主可用）。
**未验证**：priority 冲突抛错的**实测**表现（类型注释明说会抛，但没跑过）；`registerFactory` 在本仓库跑过（旧插件没用到 factory）。

## 9. 对 v0.1 实现的影响

1. **会话创建一律显式传 `sessionId`，别靠 `startSession` + 轮询。** `create({sessionId, cwd, agentPreset})` 天然幂等 adopt，冲突会明确报 `session/conflict` / `agent-preset/conflict`；而旧插件的 `uiWorkspace.startSession()` + `waitNew(15×200ms)`（client.js:1646-1680）是靠"轮询列表找新 id"猜归属，正是实施方案 §6.5 明令禁止的做法。`sessionId` 由 `projectId + roleId` 稳定派生，落库后永不变。

2. **调度必须放 Host 侧，浏览器只订阅。** 依据有二：`sessionController`、`workspaceController` 都是 Host 服务（`TypertRemoteService`，index.d.ts:17-19/20-23），Host 侧能直接 `create`/`prompt`/`follow`/`control`，不需要浏览器在场；而客户端离开页面时 `SessionReference.release()` 会拆掉本地 scope（sessions.d.ts:22-30）。→ `DispatchService`/`Reconciler` 写在 `index.js`（Host apply）里，插件 client 只做 `WorkbenchView`。

3. **幂等键用 `requestId`（Host 侧真幂等），不要自造去重表。** `hasPromptRequest` 会扫 inbox 与历史 `user/message` 的 `rpcId`，**跨重启**仍然生效（commands.js:301-302、547-561）。本项目只需要保证「同一个 dispatch 重试时复用同一个 requestId」。注意走客户端 `binding.session.prompt(...)` 时必须补第 4 参，否则等于没有幂等。

4. **模型配置是"每次派发前覆写"，不是"设一次就记住"。** `selectModel` 会后台 `saveSelection` 改全局默认。所以：读 `modelCatalog()` 校验 desired → 每次派发前显式 `selectModel` → 用返回值 `selected` 记成 `effectiveConfigSnapshot`（可能被归一化）→ 失败就明确报错，**不静默换模型**（对应实施方案 §6 三条要求）。UI 的"本次/下次"直接用 `modelSelection` 投影的 `lastUsed` / `next`。

5. **`cancel` 只能到 `cancel_requested`；`inbox` 不会被清。** 要真停，得先 `cancel` 再把排队项逐条 `updateQueue(itemId, {kind:'remove'})`（`QueueAction`，types.d.ts:149-157）；而 `updateQueue` 在 `target === 'next-turn'` 且 agent 仍 `running` 时支持 steer，否则抛 `session/steer-unavailable`（commands.js:435-436）。Attempt 状态机的 `cancel_requested → cancelled` 必须由 follow 事件确认，不能凭 `accepted:true`。

6. **左栏不要再注册 `sidebar.workspaces`。** 它是 single/root，已由 ui-workspace 声明、workspace-groups 占据。需要行内动作时只往 `sidebar.workspaces.session.menu.item` / `sidebar.workspaces.session.row.action` 这类 **list** 槽插（additive、按 order），这样不会和别人的 priority 撞（同 cell 同 priority 会抛错）。

7. **中间对话让真会话占 `main.conversation`，不要自己造 conversation。** `'conversation.content'` 是工厂、确实可复用，但 `scope: 'session-maybe'` 的绑定行为本机无法核实。最稳的是沿用旧插件的做法：`ctx.uiWorkspace.openSession(sessionId)` 让原生会话占据主区（client.js:1441-1460），插件只决定"选中哪个 session"；需要额外信息就在 `conversation.session.header.actions`（list，旧插件已用 order 40）等已有座位上加，而不是覆盖整块。

8. **P0 收尾必须补 §0.5 那六项动态验证，尤其是 U7（宿主重启）与 U8（断线重连）。** 实施方案 §8 的「重启对账」「重复事件」「两窗口租约」全都依赖这两个行为；如果实测发现 follow 不能零丢失，`Reconciler` 就必须从"增量补偿"升级为"定期全量对账 + 状态机兜底"，这会显著改变 §4 的分层预算。在此之前，任何"已通过"的结论都应写成"类型层已核实"。
