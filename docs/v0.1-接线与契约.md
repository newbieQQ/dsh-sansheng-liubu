# 三省六部工作台 · 新架构 v0.1 · 接线与契约

本文记录 v0.1 已经落地的部分：**数据层、Host 服务层、HTTP 接口、宿主接线**。
它回答三个问题：装了什么、界面能用哪些接口、哪些地方还没验证。实施方案本身见
`docs/v0.1-实施方案.md`，宿主能力的原始取证见 `docs/v0.1-宿主能力记录.md`。

> 版本口径：包版本仍是 0.9.2，**不降级**；"v0.1" 指新架构的第一版，不是包版本号。

**账本约束（store 强制，不靠调用方自觉）**

- 一个账本文件只有一个写者；`mutate()` 内所有变更同事务提交，失败整批回滚。
- `(projectId, roleId)` 绑定唯一；同一个 `sessionId` 不能同时绑两个部门/项目
  （`SESSION_CONFLICT`，带 `heldBy:{projectId,roleId}`）；换绑必须显式
  `allowReplace`，且 `bindingGeneration` 每次换绑 +1。
- 跨项目引用一律拒绝（`CROSS_PROJECT`）；实体的 `projectId` 不可改。
- 配置写入走 CAS：`saveConfig(projectId, roleId, desired, expectedRevision)`，
  期望版本不符返回冲突，避免两个标签页互相覆盖。
- 事件日志是**只读游标**：按 `seq` 追加，`listPendingEvents` 过滤未投递未处理的，
  `markEventDelivered` 只写 `deliveredAt` 不物理删除。同一 `since` 重放返回同一批事件。

## 2. HTTP 接口

前缀 `/sansheng/workbench`，全部同源。响应外层统一：

```json
{ "ok": true, "value": { } }
{ "ok": false, "error": { "code": "INVALID_STATE", "message": "…", "details": { } } }
```

| 方法 | 路径 | 请求体 / 查询 | 说明 |
| --- | --- | --- | --- |
| GET | `/bootstrap` | `?projectId=` | 一次取全：`{projects, projectId, project, seats, layout, tasks, artifacts, results, eventSeq}` |
| POST | `/project` | `hostWorkspaceId`, `displayNameCache?`, `canonicalRoot?` | 登记主机工作区↔项目；重复登记返回既有项目，不重建席位 |
| POST | `/bind` | `projectId`, `roleId`, `sessionId`, `allowReplace?` | 把某个会话绑成某部门；换绑需 `allowReplace` |
| POST | `/config` | `projectId`, `roleId`, `provider`, `model`, `reasoningEffort?`, `expectedRevision?` | 部门模型，CAS 写入；只影响该项目该部门 |
| POST | `/task` | `projectId`, `title`, `objective?`, `acceptance?`, `constraints?`, `scope?`, `ownerRoleId?`, `sourceRoleId?`, `originMessageRef?`, `returnTarget?`, `status?` | 建任务；`status:'queued'` 要求主责部门已接通 |
| POST | `/task/cancel` | `projectId`, `taskId`, `reason?` | 取消任务（终态不可再改） |
| POST | `/connect` | `projectId`, `roleId`, `sessionId?`, `agentPreset?` | 由 Host 建/定位部门会话并绑定；宿主没有会话能力时返回 `INVALID_STATE` |
| POST | `/dispatch` | `projectId`, `taskId`, `idempotencyKey`, `sourceRoleId?`, `targetRoleId`, `targetSessionId?`, `bindingGeneration?`, `packet?`, `sourceSessionId?`, `mode?`, `roleName?` | 派发任务单；有会话层时真投递，没有就只落账 `prepared`（UI 必须显示尚未接通） |
| POST | `/ingest` | `projectId`, `roleId`, `text` | 解析 Agent 输出里的契约行并落账（四动作） |
| POST | `/result` | `projectId`, `taskId`, `attemptId?`, `report?`, `runTerminal?`, `artifactRefs?`, `checks?`, `remainingItems?`, `blockedReason?`, `sourceMessageRef?`, `reportVersion?` | 登记结构化报告 / 运行终态；重复登记按 `attemptId+reportVersion` 与 `sourceMessageRef` 去重 |
| POST | `/artifact` | `projectId`, `taskId`, `displayName`, `mediaType?`, `fileRef?`, `versionOrHash?`, `verification?`, `sourceResultId?`, `revisesArtifactId?` | 直接登记成果（契约行 `registerArtifact` 之外的入口）；带 `revisesArtifactId` 时版本号自动 +1 |
| POST | `/artifact/revision` | `projectId`, `artifactId`, `instruction`, `ownerRoleId?`, `status?` | 找主责部门改一份成果：只开一条修订任务，不重跑全链 |
| GET | `/events` | `?projectId=&since=` | 长轮询（默认 25s，内部 1s 轮询账本）增量事件；`since` 之后的才算新 |

错误码：`INVALID_INPUT` / `INVALID_ROLE` / `NOT_FOUND` / `CROSS_PROJECT` /
`CONFIG_CONFLICT` / `SESSION_CONFLICT` / `DUPLICATE_PROJECT` / `INVALID_STATE` /
`DISPATCH_INVALID` / `ATTEMPT_MISMATCH` / `REPORT_INVALID` / `INTERNAL`。

## 3. 内部契约行（Agent 怎么"上报"）

Agent 不靠聊天里的"已完成"三个字更新任务，而是输出一行以 `【三省六部】` 开头的 JSON：

```
【三省六部】{"action":"dispatchTask","targetRoleId":"gongbu","title":"…","objective":"…"}
【三省六部】{"action":"reportTaskResult","taskId":"tsk_…","summary":"…","checks":["…"],"artifactRefs":["art_…"]}
【三省六部】{"action":"requestTaskInput","taskId":"tsk_…","question":"…"}
【三省六部】{"action":"syncDecision","taskId":"tsk_…","decision":"approved"}
```

- 解析：`parseContractLines(text)` 逐行匹配，坏 JSON / 未知 action 进 `invalid`，**不抛**。
- 入库：`ingestAgentOutput({projectId, roleId, text})`，四条动作各自落账。
- 模板：`describeContract()` 生成给 Agent 看的说明（已注入部门 system prompt）。

## 4. 会话与派发

### 创建（幂等）

宿主 `sessionController.create({sessionId, workspaceId|cwd, agentPreset})`：
`sessionId` 是**唯一**的幂等来源（同 id 同 cwd 同 preset → 返回同会话；
cwd 不同 `session/conflict`；preset 不同 `agent-preset/conflict`）。
`SessionCreateRequest` 里没有 `creationRequestId` —— 实施方案里那一步在宿主不存在，
我们改成"先写账本再建会话，失败留恢复记录"。

### 投递

`prompt({requestId, sessionId, mode:'queue'|'steer', content:[{text}]})`，
`requestId` 用 `attempt.id`（客户端铸造）：宿主按它去重，跨重启仍有效。
所有异常在宿主侧折叠成 `session/agent-busy`，因此**投递超时只能判 `unknown`**，
再由 `Reconciler.verifyUnknown` 查证后收口，不能直接判成功或失败。

### 取消

`cancel({sessionId})` 同步返回 `accepted:true`，但**只对已挂载的 agent 生效**、
`keepInbox:true`（排队消息会继续跑）。所以：

- 账本只推进到 `cancel_requested`；
- 要真停还得 `updateQueue({sessionId, itemId, action:'remove'})`；
- 对账看到"跑停了"才写 `cancelled`。

### 模型

- 客户端面没有 `modelCatalog()`，必须从 Host 取。
- `selectModel()` 会连带把选择存成全局默认，所以**每次派发前覆写**，
  并把实际用的 provider/model/effort 记进 `effectiveConfigSnapshot`。
- 部门配置变更只改 `desired`（CAS），不动历史；运行中的请求保持原配置。
- 模型不支持旧的 reasoningEffort 时要求重选，不透传非法枚举，不静默回退。

## 5. 完成判定

宿主"运行正常结束"≠ 业务完成。`completed` 需要三件事同时成立：

1. 运行终态是成功（`runTerminal:'succeeded'`）；
2. 有可信的结构化报告（`summary` + `checks`），且与任务验收项对得上；
3. 成果引用（`artifactRefs`）能查到实体。

只满足 1 → `needs_attention`（等人补报告）；只满足 2、1 未到 → 先登记、候终态；
用户可以主动停 → 记 `cancelled`，不算"成功但没报告"。

## 6. 项目隔离

- 账本是**单一文件**，但所有实体都带 `projectId`，服务层每次读写都校验归属；
- 绑定表主键是 `(projectId, roleId)`，不同项目可以各有自己的工部会话；
- 会话在宿主侧是全局唯一的，所以"同一会话不能再绑别的部门/项目"由账本强制；
- 配置、任务、派发、成果、事件全部按项目分片；切项目必须整树重取，
  不允许把上一个项目的 seats/tasks 混进来。

## 7. 宿主接线（index.js）

```js
import { createWorkbenchHost } from './workbench/host/index.mjs'
```

- `apply()` 里在建完政策之后 `acquireWorkbench(ctx, presetId, log)`；
  返回的 disposer 末尾 `releaseWorkbench(entry)`。
- 按**账本路径**引用计数：同一份账本只有一个写者；`apply()` 被多个 agent 调用时
  不会重复建 store，最后一个卸载时才 `dispose()`。
- 用 `ctx.root ?? ctx` 创建：工作台属于整个应用，不随单个 agent 销毁消失。
- 整体包 try/catch：工作台起不来只打日志，政策插件（prompt/工具策略）照常工作。
- 没有真实宿主服务（单测里的 mock ctx）时直接跳过，不写真实账本、不起计时器。

日志前缀 `[sansheng-liubu:workbench]`。

### 晚到的服务怎么办

`apply()` 跑的那一刻，宿主不保证 `webServer` 与 `sessionController` 都已经装好，
所以两样都按「先试一次、没到就等它到」处理：

| 依赖 | 当场没有时 | 补挂方式 | 补挂后 |
|---|---|---|---|
| `webServer` | 路由不注册，`warnings` 记一条 | `ctx.inject(['webServer'], …)` 再注册一次 | 13 条接口可用 |
| `sessionController` | 会话层为空，`hasSessions=false`，派发只落账 | `ctx.inject(['sessionController'], …)` → `shell.attachSessions(controller)` | 可以接通部门、真投递 |

两条补挂都**只做一次且幂等**：已经挂上就不再换（`attachSessions` 第二次调用返回 `true`
但保留原实例）。这样用户不必为了「接通部门」专门多重启一次 DSH。

派发钩子是恒挂的：`shell.hasSessions===true` 走真投递，否则退回 `service.dispatchTask`
只写 `prepared`——**任何时候都不会把「没接通」显示成「已发送」**。

`createWorkbenchHost(ctx, { store })` 支持注入账本（测试与嵌入场景）：注入了就用它，
不碰磁盘、不做损坏隔离，避免单测写到 `%DSH_HOME%` 下的真账本。

## 8. 尚未验证 / 已知限制

来自 `docs/v0.1-宿主能力记录.md` §8.2，按影响排序：

| 编号 | 未验证项 | 影响 | 现在的处置 |

限制：

- 账本单文件、单写者：同一个 `%DSH_HOME%` 下只能跑一个 DSH 实例写它
  （双开会被"同一账本只有一个写者"挡住，而不是写坏）。
- 事件长轮询最长 25 秒，页面隐藏时暂停，恢复时按 `since` 续读，不重放已读。
- 成果只存引用与摘要，不存文件本体。
